# Evame iPhoneアプリの実装指示

EvameのiPhoneアプリを実装する担当者向けの指示。自分の文書を執筆・保存・同期する体験を中心に据え、選んだ文書を公開できるようにする。Web側はLexicalからMarkdownを送信し、サーバーでMDAST JSONへ変換する方式へ移行中。iPhoneアプリ本体の実装は別作業で行う。

## 確定している仕様

- 最初の対象はiPhone。PCでの執筆はブラウザで行う。
- iPhoneの編集UIはネイティブで実装する。WebView上のLexicalを執筆画面として使わない。
- 編集はWYSIWYG。見出し、装飾、リスト、画像などを表示された見た目のまま編集する。
- 執筆にはログインが必要。ログイン前に原稿を作ったり、匿名の原稿を後からアカウントへ追加したりするフローは作らない。
- ログイン済みアカウントの文書はオフラインでも作成・編集・保存できる。通信が戻ったら同期する。
- 端末の文書データはSQLite、画像はアプリの永続ファイル領域に保存する。
- クラウドDBはTurso。アプリからDBへ直接接続せず、認証されたAPIを使う。
- サーバーの文書保存形式は既存のMDAST JSON。WebのLexical独自JSONを共通保存形式にはしない。
- Markdownの入出力はCommonMarkとGFMを対象にする。
- 自分の文書をMarkdownファイルと画像として書き出し、Gitでバックアップできるようにする。Git側の編集を取り込む双方向Git同期は今回の要件に含まれない。
- 版をまたぐ段落照合を維持する。変更していない段落の翻訳・投票は引き継ぐ。
- 翻訳は公開をきっかけに実行する。端末への自動保存やクラウド同期のたびに翻訳を開始しない。
- PCブラウザにローカル原稿保護やオフライン執筆を新設する作業は、今回の依頼には含まれない。

## 作業範囲

SwiftUIを画面構成の基本候補とし、編集部分はUIKit/TextKitを含むネイティブの編集基盤で検証する。具体的なエディタライブラリ、最低対応iOSバージョン、SQLiteアクセスライブラリは、対象機能を確認してから決める。Lexical Webの採用を理由にLexical iOSも採用済みと扱わない。Lexical iOSは公式にプレリリース・サポート保証なしと記載されている。

最初に、日本語の変換中入力、選択範囲、Undo/Redo、画像、リスト、GFMの表を含む小さな編集画面を実機で検証する。入力体験と文書の往復変換を確認してからアプリ全体へ組み込む。

## 保存と編集

1. ログイン済みアカウントの文書をSQLiteから開く。
2. 編集内容を端末へ自動保存する。ネットワークの成功を端末保存の完了条件にしない。
3. 本文、メタデータ、同期待ちの変更を整合する形で保存する。
4. 「端末に保存済み」「同期中」「同期済み」「同期に失敗」を区別する。
5. アプリの終了・再起動後にも、未同期の本文と画像を復元する。

SQLiteには文書識別子、アカウント識別子、タイトル、本文、最後に同期したサーバーの版、未同期変更の状態など、実際に必要な情報を保存する。既存のslugと端末内の識別子を混同しない。タイトルやslugの変更で別文書に分裂させない。

端末本文の正本をMarkdownにするか、MDAST互換の構造にするかは、ネイティブエディタの往復検証で確定する。APIとの本文交換はMarkdownを基本にし、同じ本文のMarkdownとJSONを独立した正本として管理しない。編集中の選択・IME状態などは文書の永続データから分ける。

## Markdownの互換性

見出し、段落、強調、リンク、画像、引用、順序付き・順序なしリスト、コード、改行と、GFMの取り消し線・チェックリスト・表を対象にする。既存のX埋め込みも、URLの情報を失わずに扱う。

「取り込めた」だけでは完了にしない。同じ文書をWebとiPhoneで開き、編集して保存し直しても、本文・画像・表・リンクの内容と構造が保たれることを確認する。元の空白や記号の完全一致を保証するかは未確定であり、保証済みと表示しない。

未対応の構文や既存の拡張情報を読み込み時に削除しない。編集可能にするか、元データを保った表示にするかを決める。保存できない状態を黙ってプレーンテキストに変換しない。

## 画像

- 写真の取り込み時に、アプリが所有する永続ファイル領域へコピーする。一時URLや写真ライブラリの権限だけを頼りに保存済みとしない。
- 本文と画像を端末内の安定した識別子で関連付ける。本文には端末固有の絶対パスを同期しない。
- 未送信画像がある文書は、画像のアップロードと本文の参照先の確定まで「同期済み」にしない。
- 再送で同じ画像を増殖させないよう、サーバー側との対応関係を保存する。
- アップロードに失敗しても端末の画像と本文を残し、再送できるようにする。
- 端末から画像を削除するのは、文書からの参照と未同期変更を確認してから行う。

画像原本の保持期間、クラウド側の非公開画像のアクセス制御、同期対象画像のダウンロード範囲は未確定。現行の画像アップロードAPIが返すURLだけを根拠に、非公開原稿の画像もアクセス制御されていると扱わない。

## 同期

本文と画像の端末保存を先に完成させる。APIの未整備部分はモックで分離し、存在しないサーバー機能を実装済みと仮定しない。

同期には取得時の版を添える。同じ文書がサーバー側でも変わっていた場合、端末の原稿を無条件で上書きしない。自動統合の範囲や競合解決UIはまだ決定していないため、両方の内容を保持して停止・再試行できる状態を作り、その後の方針を確認する。

通信が切れた直後にサーバー側だけ保存済みになる場合も考慮する。再送や応答待ちの間にさらに編集された場合、送信した版と現在の端末版を区別する。古い応答で新しい変更を「同期済み」にしない。

アプリの起動・復帰時と利用中に同期し、手動の再試行操作を用意する。iOSのバックグラウンド実行を常時接続や即時同期の保証として扱わない。

アカウントを切り替えても、別アカウントの原稿を送信・表示しない。認証情報はKeychainに保存する。ログアウト時の未同期データの扱い、削除の伝播とごみ箱、履歴保持期間は要決定。未同期原稿を自動的に破棄する実装は先行させない。

## 現行サーバーAPI

以下は調査時点のmainの実装。iPhone向けのAPIがすべて完成しているという意味ではない。実装時には最新コードを確認する。

### 文書の取得

`GET /api/sync/pull` はBearer認証で、そのユーザーのARCHIVE以外のページを返す。

```json
{
  "pages": [
    {
      "slug": "example-note",
      "revision": "server-issued-revision",
      "title": "メモ",
      "body": "## 見出し\n\n本文\n",
      "published_at": null
    }
  ]
}
```

現行レスポンスには文書の内部ID、親子関係、タグ、削除の記録、差分取得用のカーソルがない。受信一覧に文書がないことだけを理由に、端末の未同期原稿を削除しない。

### 文書の送信

`POST /api/sync/push` はBearer認証でMarkdownを受け取る。

```json
{
  "inputs": [
    {
      "slug": "example-note",
      "expected_revision": null,
      "title": "メモ",
      "body": "## 見出し\n\n本文\n",
      "published_at": null
    }
  ]
}
```

新規文書の`expected_revision`は`null`。更新時には取得した版を送り、成功時の`applied_revision`を保存する。版は本文以外にも依存し、サーバーでMarkdownの正規化も行うため、端末で独自に計算した値をサーバーの版として扱わない。

現行APIは競合があるとHTTP 409を返す。新規作成を含む適用は201、その他の適用・変更なしは200。複数件の送信は全件をまとめた単一トランザクションではないため、通信失敗後は保存状況の再確認が必要。

**現行pushは`published_at`から公開状態を決める。** 原稿の自動同期として無条件に流用しない。公開状態を維持した保存と、利用者が明示的に行う公開操作をどう区別するか、サーバー担当と契約を確定する。公開を伴う処理では既存の翻訳開始経路も確認する。

### 認証と画像の未整備部分

- `/api/sync/cli-login`はlocalhost/127.0.0.1へのHTTPコールバックを許可するCLI向けの実装。iPhoneの認証コールバックとしてそのまま使えない。
- iPhoneからのログインはシステムの認証セッションを使う方式を基本候補とし、コールバック・トークン受け渡し・失効をサーバー担当と決める。執筆用WebViewへ既存ログイン画面を埋め込んで成立させない。
- `/api/reader-actions?action=uploadImage`は現行ではWebセッションの認証と同一オリジン検証を前提にする。sync APIのBearerトークンを渡せば使えると仮定しない。
- モバイル認証で画像を送信できるAPIと、画像参照の契約が必要。本文APIとの認証を揃える。
- 本番アプリにTursoの認証情報を組み込まない。

## 公開と翻訳

執筆・端末保存・同期と、公開操作を区別する。公開済み文書を編集した際に即座に公開本文を更新するか、「更新を公開」まで下書きとして保持するかは未確定。後者を採用済みとして実装しない。

翻訳はサーバーで処理する。段落IDや照合用ハッシュをiPhone独自の規則で作らず、既存の段落抽出・照合・翻訳選定・投票の仕組みを維持する。変更した段落の翻訳を変更前と同じ翻訳として強制的に引き継がない。

既存の親子ページ、コメント、翻訳、投票などの機能を、エディタ実装の都合で削除しない。今回の会話で列挙されたサイト数、テーマ、料金、ごみ箱30日などの推奨案は、確定事項ではない。

## 書き出し

Markdownと画像をまとめて持ち出せるようにし、画像リンクは相対パスへ変換する。オフラインで書き出す場合も、端末にある未同期の最新原稿と画像を対象にする。メタデータの形式やファイル名はWeb・CLIと整合させてから固定する。翻訳・投票を含むサービス全体の完全バックアップまで保証するかは未確定。

## 実装の順序と完了条件

1. ネイティブ編集画面の試作。日本語変換中の入力、選択、Undo/Redo、画像・表・リストを実機確認する。
2. SQLiteと画像ファイルへの端末保存。オフライン編集後にアプリを終了しても復元できることを確認する。
3. 共通Markdownの往復テスト。Webで作った文書をiPhoneで編集し、その逆も内容を保持することを確認する。
4. 認証と本文・画像APIの契約をサーバー担当と合わせ、モックから実APIへ接続する。
5. 競合、401、通信切断、再送、同期中の追加入力、アカウント切り替えのテストを行う。
6. Markdownと画像の書き出しを検証する。

実装は対象リポジトリの規約と再現可能な環境に従い、振る舞いのテストを先に書く。未実装APIや未検証の端末挙動が残る場合、完了した機能と区別して報告する。
