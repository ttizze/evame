# Evame iPhoneアプリの実装指示

EvameのiPhoneアプリを実装する担当者向けの指示。自分の文書を執筆・保存・同期する体験を中心に据え、選んだ文書を公開できるようにする。Web側はLexicalからMarkdownを送信し、サーバーでMDAST JSONへ変換する方式へ移行している。

現行コードの挙動は、この文書を書いた時点の実装に基づく。実装時には最新コードを確認する。

## 目的と対象

iPhoneで次のことをできるようにする。

- ログインし、自分の文書を一覧・作成・編集する。
- 見出し、装飾、リスト、画像、表を、表示された見た目のまま編集する。
- オフラインでも端末へ保存し、通信が戻ったら同期する。
- 選んだ文書を公開する。
- 自分の文書をMarkdownと画像として書き出す。

対象画面は、ログイン、文書一覧、編集、同期状態と競合の表示、公開操作、書き出し。閲覧、コメント、投票、親子ページやタグの管理をネイティブで作ることは今回含まない。ただし、サーバー上のこれらのデータを同期の都合で壊さない。

PCでの執筆はブラウザで行う。PCブラウザにオフライン執筆やローカル原稿保護を新設することは今回含まない。

## 確定している仕様

- 編集UIはネイティブで実装する。WebView上のLexicalを執筆画面として使わない。
- 執筆にはログインが必要。ログイン前の原稿作成や、匿名原稿を後からアカウントへ移すフローは作らない。
- 端末の文書データはSQLite、画像はアプリの永続ファイル領域に保存する。
- クラウドDBはTurso。アプリはDBへ直接接続せず、認証されたAPIを使う。本番アプリにTursoの認証情報を組み込まない。
- サーバーの文書保存形式は既存のMDAST JSON。APIとの本文交換はMarkdownを使う。WebのLexical独自JSONは共通形式にしない。
- Markdownの対象はCommonMarkとGFM。
- 版をまたぐ段落照合を維持し、変更していない段落の翻訳・投票を引き継ぐ。段落IDや照合用ハッシュはサーバーが作り、iPhone独自の規則で作らない。
- 翻訳は公開をきっかけにサーバーで実行する。端末保存や同期のたびに翻訳を開始しない。変更した段落の翻訳を、変更前と同じ翻訳として強制的に引き継がない。
- 執筆・端末保存・同期と、公開操作を区別する。公開は利用者の明示操作として実行する。
- 認証情報はKeychainに保存する。

## 担当範囲

iPhone担当は、アプリ本体、端末保存、同期クライアントとそのテストを実装する。Web・サーバーAPIの改修はサーバー担当が行う。

次節の契約が満たされるまで、未整備のAPIはモックで検証する。独立したモックサーバーが必要かは検証方法に応じて決める。存在しないサーバー機能を実装済みと仮定しない。

## サーバー担当との契約

実APIでの同期を有効にする前に、サーバー担当と次の契約を確定する。各項目には現行の挙動と、契約が必要な理由を書く。

### 文書の識別と新規作成

- 現行APIはslugで文書を特定し、安定したサーバー文書IDを返さない。slugを変えて送信すると新規文書になる。現行APIを使う間は作成後のslug変更を禁止する。変更を提供する場合は、サーバー文書IDで同じ文書を更新し、版を検証してからslugを変える契約を先に追加する。
- `pages.slug`は全ユーザーで一意だが、pushは送信者のページだけを検索する。他ユーザーと同じslugで新規作成すると、一意制約違反でサーバーエラーになる。端末で十分長い乱数slugを採番するか、サーバーで採番して端末の識別子と対応付けるかを決め、衝突時の応答を定める。
- 現行pushは、サーバーに文書がなければ`expected_revision`があっても新規作成する。削除済みの文書への古い更新で文書が復活する。「新規作成」と「存在しなくなった文書の更新」を区別して応答する契約が必要。

### 版の検証と再送

- 版の検証と書き込みは同一トランザクションで行う必要がある。現行では`build-judgments.ts`の事前判定と`execute-push.ts`の書き込みの間にWeb編集が割り込める。文書ごとの保存自体はトランザクション内だが、版の判定がその外にある。
- この契約はWebの保存にも適用する。現行Webの保存には版検証がないため、先に開いたWeb編集画面が、iPhoneの同期成功後に保存すると同期結果を上書きできる。Webも読み込み時の版を送り、古い版からの保存は、編集中の本文を保持したまま競合として返す。
- 現行の判定は、版の不一致を内容の同一判定より先に評価する。更新は成功したが応答だけ失われた場合、同じ内容を古い版で再送すると409になる。また`NO_CHANGE`の応答は版を返さない。同一内容の再送には現在の版を返す契約が必要。
- サーバーはMarkdownを正規化して保存し、版はその結果から計算する。適用時と変更なしの応答で、正規化後の本文と版を返す契約が必要。端末でサーバーの正規化と版計算を再現しない。
- 応答喪失後の回復で送信内容とpull結果を照合する場合、送信時点のタイトル・本文・公開状態に加え、`published_at`も`null`またはUTCのISO 8601日時へ正規化して照合する。すべての一致を確認できた場合だけ取得した版を採用し、その後の端末の追加入力を同期済みにしない。現行pullは公開状態を返さないため、この契約が整うまで公開状態の照合による回復は有効にしない。
- 1件でも競合があると、同じリクエストの全件が適用されない。複数文書をまとめた適用は原子的ではない。iPhoneは1文書を1リクエストで送る。

### 本文の保存と公開状態

- 現行pushは`published_at`から公開状態を決める。省略すると`null`として扱い、適用される更新では非公開になる。
- Webの公開・非公開操作は`status`だけを変え、同期の版は`status`を含まない。pullも公開状態を返さない。そのため端末は公開状態の変化を検知できず、次の本文同期で公開・非公開を元に戻し得る。例: Webで公開した`published_at`が`null`の文書を、iPhoneで編集して送ると非公開になる。
- 本文の保存は公開状態を変えず、公開は利用者の明示操作として別に扱う契約にする。pullは公開状態を返し、`status`を含む版の原子的な検証を行う。Webで非公開にしても公開日時は変わらないため、古い版と公開日時による本文同期で再公開しないことも検証する。
- 公開済み文書の編集を即時に公開本文へ反映するか、「更新を公開」まで下書きにするかは未決定。後者を採用済みとして実装しない。

### 公開・翻訳・配信

- 現行pushは翻訳ジョブを作らない。sync経由で作成した文書の`sourceLocale`は`ja`に固定されている。iPhoneの明示公開から、Webの公開と同じ翻訳処理を開始できる契約と、`sourceLocale`の決め方を定める。
- 公開APIの成功条件は、公開状態の保存、必要な翻訳ジョブの作成とキュー投入、対象の配信キャッシュの無効化とする。翻訳処理の実行・完了やHTMLの再生成は待たない。現行のsync/pushも、サーバーの入口で配信キャッシュの無効化を待つ。DB保存後にキュー投入や無効化が失敗した場合の再送を契約に含める。

### 認証

- `/api/sync/cli-login`はlocalhost/127.0.0.1へのHTTPコールバックを前提にしたCLI向け実装で、iPhoneでは使えない。
- iPhoneのログインはシステムの認証セッションを基本候補とし、コールバック、トークンの受け渡し、有効期限、再認証、失効、アカウントの識別を定める。執筆用WebViewへ既存のログイン画面を埋め込まない。
- 同期APIのBearer認証は、7日で期限が切れるセッショントークンか、期限のない個人アクセストークンを受け付ける。同期APIにはトークン更新の契約がない。更新方式は契約で決める。

### 画像

- `/api/reader-actions?action=uploadImage`はWebセッション認証と同一オリジン検証を前提にしており、Bearerトークンでは使えない。モバイル認証で使える画像アップロードAPIが必要。
- 現行pushは、本文中の外部画像URLを取得して再アップロードし、URLを書き換える。アップロードは競合判定より前に実行され、毎回新しい保存先を作る。応答喪失や競合のたびに画像が増える。本文には確定済みのEvame画像URLだけを送ること、画像アップロードを再送しても重複しない識別子を持つことを契約にする。
- 端末は確定した画像URLを送信時点の記録にも保持し、応答喪失後はその記録とpull結果を照合する。現行の外部画像の取り込みはランダムなURLへ書き換えるため、この契約が整うまで画像付きpushの応答喪失を本文一致で回復できると仮定しない。
- 非公開原稿の画像のアクセス制御、画像原本の保持期間、同期で端末へダウンロードする画像の範囲は未決定。現行APIが返すURLを根拠に、非公開原稿の画像がアクセス制御されていると扱わない。

### 取得

- 現行pullは、保存済み本文に変換できないノードが1つでもあると全体が失敗する。変換できない文書があっても他の文書を返し、該当文書を識別できる契約にする。
- 現行pullには、親子関係、タグ、削除の記録、差分取得のカーソルがない。pullの一覧に文書がないことだけを理由に、端末の未同期原稿を削除しない。
- 現行pullは毎回全文書の本文を返す。想定する文書数で通信量と応答時間を計測し、問題があれば版の一覧だけを返すAPIなどを検討する。最初からの必須条件にはしない。

### 送信できる原稿の条件

現行pushは、タイトル必須、本文100万文字以内、1リクエスト100件以内。無題の原稿なども端末への保存は成功させ、送信条件を満たさない理由を利用者に示す。

## ネイティブ編集

### 試作で確認すること

SwiftUIを画面構成の基本候補とし、編集部分はUIKit/TextKitを含むネイティブの編集基盤で検証する。Lexical Webの採用を理由にLexical iOSを採用済みと扱わない。Lexical iOSは公式にプレリリース・サポート保証なしと記載されている。

最初に、日本語の変換中入力、選択範囲、Undo/Redo、画像、リスト、GFMの表を含む小さな編集画面を実機で作る。入力体験と文書の往復変換を確認してから、アプリ全体へ組み込む。

表は、本文中で直接編集する方式と、表専用の編集画面を開く方式を比較する。セルの内容と配置、Undo、日本語入力を保てるかで判断する。

### 対応する構文

- 見出し、段落、強調、リンク、画像、引用、順序付き・順序なしリスト、コード、改行。
- GFMの取り消し線、チェックリスト、表。
- X埋め込み。サーバーはX/Twitterのリンク1つだけの段落として保存し、表示時に埋め込みへ変換する。エディタ内では埋め込みとして表示してよいが、保存時は単独のリンク段落に戻す。

### 編集に対応できない構文の保持

編集に対応できない構文も、読み込み時に削除せず、内容と構造を失わずに再保存できるようにする。Markdown断片を持つ読み取り専用ブロックを第一候補として試作する。脚注と定義のように離れたブロック同士の関係も保つ。Web側のLexicalにも、MDASTから再生成したMarkdownを保持する先例がある（`src/app/[locale]/_components/editor/markdown.ts`）。ただし、元の空白・記号の完全一致を保証するものではない。

保存できない状態を黙ってプレーンテキストに変換しない。サーバーがMarkdownとして返せない情報は端末では保持できないため、サーバーとの契約で扱う（「取得」を参照）。

### 端末本文の正本

Markdownを第一候補として検証する。APIとの交換形式、書き出しと一致し、同じ本文を二重に持たずに済むため。往復検証で成立しなければ、理由を記録して別の形式を選ぶ。同じ本文のMarkdownとJSONを、独立した正本として両方保存しない。

選択範囲やIMEの状態など、編集中の状態は文書の永続データと分ける。

### 往復の合格基準

- Webで作った代表文書を共通のテストデータにする。表、入れ子のリスト、チェックリスト、複数段落を含む引用、画像、X埋め込み、コード、読み取り専用で保持する構文を含める。
- 編集しない往復では、サーバーで正規化したMDASTが位置情報を除いて等価であること。Webのテスト（`src/app/[locale]/_components/editor/markdown.test.ts`）に先例がある。
- 編集した往復では、意図した差分だけが生じること。
- 画像は、端末の画像識別子とサーバーのURLを固定した対応表で検証する。
- 翻訳・投票の引き継ぎはMDASTの比較では証明できない。代表文書に翻訳と投票を付け、別の段落を編集した後も対象段落のIDと関連データが残ることを、サーバー担当が整備する結合テストで確認する。同じ文の繰り返し、リスト、表のセルを含める。

## 端末保存

1. ログイン済みアカウントの文書をSQLiteから開く。
2. 編集内容を端末へ自動保存する。ネットワークの成功を端末保存の完了条件にしない。
3. 本文、メタデータ、同期待ちの変更を整合する形で保存する。
4. 「端末に保存済み」「同期中」「同期済み」「同期に失敗」を区別して表示する。
5. アプリの終了・再起動後も、未同期の本文と画像を復元する。

SQLiteには、端末の文書識別子、アカウント識別子、slug、タイトル、本文、最後に同期したサーバーの版、未同期変更の状態など、実際に必要な情報を保存する。端末の識別子とslugを混同しない。

### 画像

- 写真の取り込み時に、アプリが所有する永続ファイル領域へコピーする。一時URLや写真ライブラリの権限に頼って保存済みとしない。
- 本文と画像を端末内の安定した識別子で関連付ける。端末固有の絶対パスを同期しない。
- 未送信の画像がある文書は、画像のアップロードと本文の参照先の確定まで「同期済み」にしない。
- 再送で画像が増えないよう、端末の画像とサーバーの画像の対応を保存する。
- アップロードに失敗しても、端末の画像と本文を残して再送できるようにする。
- 端末から画像を削除するのは、文書からの参照と未同期変更がないことを確認してからにする。

## 同期

### 送信と応答の反映

- 送信は文書ごとに直列化する。
- 送信時に、送った内容と端末の版番号を記録する。
- 成功応答の版は記録する。ただし送信後に追加の入力があれば、その文書は未同期のままにする。古い応答で新しい変更を「同期済み」にしない。
- 正規化後の本文は、送信時の端末版と現在の端末版が一致する場合にだけ反映する。
- pullでは、取得開始前からある未同期変更と取得中の編集の両方を守る。変更がある本文を上書きせず、受信した内容は別に保持して照合する。

### 応答を受け取れなかった場合

送信時の内容と版を保持し、サーバーと合意した再送・結果確認の契約に従って保存結果を確定する。確定できない場合は、本文と送信記録を保持して停止する。その後の追加入力を同期済みにしない。現行APIの制約は「版の検証と再送」を参照する。

### 競合

同期には取得時の版を添える。サーバー側でも同じ文書が変わっていた場合、端末の原稿を無条件で上書きしない。自動統合の範囲と解決UIは未決定のため、両方の内容を保持して停止・再試行できる状態を作る。

### 認証切れとアカウント

- 401を受けたら同期を止め、未同期の原稿を保持したまま再ログインを求める。
- アカウントを切り替えても、別アカウントの原稿を送信・表示しない。
- 未同期原稿を自動で破棄する実装を先に作らない。

### 同期のタイミング

アプリの起動時、復帰時、利用中に同期し、手動の再試行操作を用意する。iOSのバックグラウンド実行を、常時接続や即時同期の保証として扱わない。

## 書き出し

Markdownと画像をまとめて書き出し、画像リンクを相対パスに変換する。オフラインでも、端末にある未同期の最新原稿と画像を対象にする。Git側で編集した内容を取り込む双方向Git同期は今回の対象外。メタデータの形式とファイル名、未取得の画像がある場合の扱い、Gitバックアップの範囲は未決定事項に従う。

## 開発環境と配置

- 対象リポジトリの規約と再現可能な環境に従う。このリポジトリのWeb・API用コマンドはNix環境で実行する。
- アプリは同じリポジトリの`apps/ios`に置く。編集試作の構成と再現コマンドは`apps/ios/README.md`を参照する。Xcode 26.6とiOS SDK 26.5を使い、XcodeGenは既存のNix環境、Swift依存は`Package.resolved`で固定する。Biomeやtypecheckなど、TypeScript向けの検証をSwiftにそのまま適用しない。
- 振る舞いのテストを先に書く。

## 実装工程と完了条件

### iPhone側

1. 編集画面の試作。日本語変換中の入力、選択、Undo/Redo、画像・表・リストを実機で確認する。
2. SQLiteと画像ファイルへの端末保存。オフラインで編集した後にアプリを終了しても復元できる。
3. Markdownの往復テスト。共通テストデータが合格基準を満たす。
4. APIをモックした同期テスト。競合、401、通信切断、再送、同期中の追加入力、アカウント切り替え、送信条件を満たさない原稿、応答喪失からの回復をテストする。
5. Markdownと画像の書き出し。

### サーバー側

「サーバー担当との契約」の各項目を実装する。iPhone側と並行して進める。

### 結合

6. 実APIへの接続。モックで通したテストを実APIで再実行する。加えて、版の判定後・保存前にWebで変更しても上書きしないこと、先に開いたWeb編集画面がiPhoneの同期後に保存しても同期結果を失わないこと、slug変更で文書が重複しないことを確認する。
7. Webで作った文書をiPhoneで編集し、その逆も内容と翻訳・投票を保つことを確認する。
8. 公開すると翻訳ジョブが受け付けられ、公開URLへのアクセスで更新内容が表示されることを確認する。

未実装のAPIや未検証の端末挙動が残る場合は、完了した機能と区別して報告する。

## 付録: アプリ用API

CLI・GitHub Actions向けの`/api/sync/*`は挙動を変えず、アプリ用に`/api/app/*`を分けた。同期APIの課題（版の判定と書き込みが別、本文の同期で公開状態が変わる、削除済み文書の復活、画像の重複）は、こちらの契約で解消する。公開済み文書の編集はWebと同じく保存時点で公開ページへ反映する。

| API | 契約 |
|---|---|
| `GET /api/app/login?code_challenge=…` | システムの認証画面で開く。未ログインならWebのログインへ送り、戻った後に許可画面を表示し、本人が同一オリジンPOSTで許可した後だけ`evame-editor://auth?code=…`で5分間・一回限りのコードだけを返す（PKCE S256）。 |
| `POST /api/app/token` | `{code, code_verifier}`を端末用トークン（期限なし、名前`iPhone`の個人用アクセストークン）に交換する。コードは照合の成否にかかわらず一度で使えなくなる。 |
| `DELETE /api/app/token` | 要求に使った端末用トークンだけを失効させる。 |
| `GET /api/app/documents` | `{documents: [{slug, title, body, status, revision}], failed: [{slug}]}`。アーカイブ以外の自分の文書を新しい順に返す。Markdownへ変換できない文書は`failed`へ分ける。 |
| `PUT /api/app/documents/:slug` | `{title, body, expected_revision, locale}`。slugは端末で`[0-9a-z]`12文字以上を採番する（Webと同じ形）。版の確認と書き込みを同じトランザクションで行い、公開状態は変えない。新規は下書きで作る（201）。送った内容が現在と同じなら版が古くても変更なし（200、現在の文書）として応答喪失後の再送を回復できる。競合は409で`{reason, document}`を返す（`revision_mismatch`は現在の文書、`missing`・`slug_taken`は`null`、`archived`）。 |
| `PUT /api/app/documents/:slug/status` | `{status: "PUBLIC" \| "DRAFT", expected_revision}`。公開するたびにWebと同じく保存済みの翻訳先へ翻訳を始める。翻訳の投入は状態の保存の後に行う。 |
| `POST /api/app/images` | multipartの`id`（端末の画像のUUID）と`image`。保存先を利用者と画像IDで決めるため、送り直しても同じURLになり画像は増えない。 |

Webでログイン済みでも、本人のハンドルと文書・画像の読み書き、公開状態の変更権限を表示して許可を求める。GETではコードを発行せず、認証済みの同一オリジンPOSTだけで一回限りのコードを発行する。画像IDは大文字・小文字を区別せず、サーバーで小文字にそろえる。新規文書のslugは端末の採番規則に従うが、既存のWeb・CLI文書は取得したslugを保って更新できる。

版は題名・正規化後の本文・公開状態から計算する（Webでの公開・非公開も検知できる）。保存の変換はWebと同じ経路（画像の取り込み・言語判定・段落照合）で行い、外部への通信を含む変換はトランザクションの前に済ませる。公開中の文書の保存と公開状態の変更は公開ページのキャッシュを無効化し、下書きの保存は無効化しない。

## 付録: 現行の同期API

### 文書の取得

`GET /api/sync/pull` はBearer認証で、そのユーザーのARCHIVE以外のページを返す。

```json
{
  "pages": [
    {
      "slug": "example-note",
      "revision": "server-issued-revision",
      "title": "メモ",
      "body": "## 見出し\n\n本文\n",
      "published_at": null
    }
  ]
}
```

### 文書の送信

`POST /api/sync/push` はBearer認証でMarkdownを受け取る。新規文書の`expected_revision`は`null`。更新時には取得した版を送り、適用されたら応答の`applied_revision`を保存する。

```json
{
  "inputs": [
    {
      "slug": "example-note",
      "expected_revision": null,
      "title": "メモ",
      "body": "## 見出し\n\n本文\n",
      "published_at": null
    }
  ]
}
```

競合があるとHTTP 409を返す。新規作成を含む適用は201、その他の適用と変更なしは200。
